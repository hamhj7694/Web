# 오메추 | 오늘의 메뉴 결정을 돕는 음식 추천 웹서비스 MVP

> **“오늘 뭐 먹지?”라는 일상적인 선택의 고민을, 메뉴 추천에서 음식 정보 확인·주변 식당 탐색까지 연결했습니다.**

오메추는 음식 선택에 필요한 조건을 화면에서 입력하고, 메뉴 추천 결과를 확인한 뒤 음식 정보와 주변 식당을 더 살펴볼 수 있도록 구성한 **웹서비스 프로토타입(MVP)**입니다. HTML/CSS/JavaScript 프론트엔드와 PHP·SQL 기반 API, 지도 연동 코드를 연결하는 데 초점을 맞췄습니다.

**[상세 포트폴리오 (Notion)](https://app.notion.com/p/401c753ff28a8032b9f4d134b6431bda)** · [상위 저장소](https://github.com/hamhj7694/Web) · [기획 자료](https://github.com/hamhj7694/Web/tree/main/finalMission/omechu)

> **검증 범위:** 이 문서는 저장소의 구현 코드와 기획 산출물을 기준으로 작성했습니다. 전체 기능의 운영 서버 배포·DB 연결·실기기 통합 테스트를 완료했다는 의미는 아닙니다. 사용자 지표나 성능 수치는 확인된 자료가 없어 제시하지 않습니다.

## 1. 문제 정의와 사용자 경험

단순히 음식 이름 하나를 보여주는 데 그치지 않고, **결정 → 정보 확인 → 주변 장소 탐색**까지 이어지는 흐름을 구성했습니다.

| 사용자 단계 | 화면/기능 | 설계 의도 |
| --- | --- | --- |
| 메뉴 결정 | 랜덤 추천·룰렛 UI | 선택의 시작을 가볍게 만듦 |
| 조건 반영 | 음식 카테고리·상황·시간대 선택 | 사용자가 원하는 조건을 입력 |
| 결과 확인 | 추천 음식 카드·다시 추천 | 추천 결과를 이해하고 다음 행동 선택 |
| 추가 탐색 | 푸드 위키 | 음식의 정보·태그·추천 수 등을 살펴보기 |
| 주변 탐색 | 지도 | 키워드·지역·식당 검색으로 실제 장소 알아보기 |
| 참여 흐름 | 로그인·마이페이지·추천·댓글 관련 화면 | 사용자 참여 기능을 위한 구조 |

이 프로젝트의 핵심은 **추천 알고리즘 자체의 고도화**보다 입력 조건, 음식 데이터, 결과 화면, 탐색 기능을 **하나의 웹 애플리케이션 흐름**으로 연결한 점입니다.

## 2. 동작 구조

```text
사용자
  ├─ 바로 추천받기
  └─ 맞춤 조건 선택(카테고리·상황·시간대)
           ↓
    JavaScript 이벤트·요청
           ↓
      PHP 추천 API
           ↓
    음식 데이터베이스 조회
           ↓
     음식 1건 JSON 응답
           ↓
  추천 결과를 localStorage에 저장
           ↓
    결과 페이지 이동·표시
       ├─ 다시 추천
       ├─ 푸드 위키
       └─ 지도·주변 식당 탐색
```

- **프론트엔드:** HTML, CSS, Vanilla JavaScript, DOM 이벤트, `fetch`, `localStorage`
- **백엔드:** PHP API, MySQLi 준비된 문장(Prepared Statement), JSON 응답
- **외부 서비스:** Kakao Maps 기반 지도·장소 검색, 외부 메뉴 정보 API 프록시 코드
- **데이터:** 음식의 이름·종류·태그·상황·시간대·추천 수 등을 다루는 데이터 구조

## 3. 핵심 구현 A — 조건 기반 음식 추천

[코드: `js/index.js`](./js/index.js) · [코드: `backend/api/omechu/random.php`](./backend/api/omechu/random.php)

1. 사용자가 카테고리·상황·시간대를 선택하면 JavaScript에서 선택값을 읽습니다.
2. PHP API가 `category`, `situation`, `time` 쿼리 파라미터를 받아 조회 조건을 구성합니다.
3. 활성 상태의 음식 데이터 중 조건과 일치하는 후보를 찾고 **무작위로 1개** 반환합니다.
4. 프론트엔드는 결과를 받아 브라우저에 저장하고 결과 화면으로 이동합니다.
5. 후보가 없거나 요청이 실패하면 별도 안내를 표시하도록 분기했습니다.

**구현상 판단과 한계**

- SQL 입력 조건에는 **준비된 문장과 파라미터 바인딩**을 적용했습니다.
- 현재 서버 조회는 카테고리·상황·시간대 각각 **단일 값** 중심이며, 프론트엔드에서도 그룹별 첫 번째 선택값을 API에 전달합니다. 따라서 UI의 복수 선택이 항상 복수 조건 검색으로 반영되지는 않습니다.
- 무작위 선택에 `ORDER BY RAND() LIMIT 1`을 사용합니다. 데이터 규모가 커지면 조회 비용을 다시 검토해야 합니다.
- 상황·시간대의 JSON 문자열 컬럼을 `LIKE`로 검색하므로 향후 데이터 구조 정규화와 다중값 조건 처리가 개선 과제입니다.
- **AI 개인화 추천 모델이나 학습형 랭킹 알고리즘은 사용하지 않았습니다.**

## 4. 핵심 구현 B — API 응답에서 사용자 화면까지

[코드: `js/result.js`](./js/result.js)

추천 요청 이후 화면이 끊어지지 않도록 다음 처리를 구현했습니다.

- **비동기 요청:** `fetch`로 PHP API의 JSON 응답을 읽고 성공·실패에 따라 다른 안내를 제공
- **데이터 정규화:** 누락된 이름·카테고리·이미지 경로 등 UI에 필요한 값을 기본값으로 보완
- **화면 간 상태:** 추천 음식과 요청 시각·조건 등을 `localStorage`로 전달
- **후속 행동:** 결과 재추천, 음식 정보·지도 이동, 공유 관련 UI 구성
- **피드백:** 버튼 클릭 후 룰렛 애니메이션으로 추천 과정을 시각화

단순 화면 제작을 넘어 **사용자 입력 → API 요청 → 데이터 응답 → 화면 상태 갱신**으로 이어지는 웹 애플리케이션 흐름을 구현한 사례입니다.

## 5. 핵심 구현 C — 음식 탐색과 지도 검색

### 푸드 위키

[코드: `js/wiki.js`](./js/wiki.js)

음식 이름·태그 검색, 카테고리 필터, 추천순·최신순·댓글순 정렬, 페이지 단위 표시를 위한 클라이언트 로직을 구성했습니다. 관련 PHP API에는 목록·상세·추천·댓글 등 사용자 참여 기능을 위한 코드가 포함되어 있습니다.

### 지도

[코드: `js/map.js`](./js/map.js)

Kakao Maps 기반으로 현재 위치·검색 지역·지도 중심 등 검색 기준을 구분하고, 입력 키워드의 종류에 따라 검색을 분기하는 로직이 있습니다.

예시로 `신림역 파스타` 같은 표현은 **지역 + 음식**, `파스타`는 **음식**, `신림역`은 **장소**로 분류하도록 처리합니다. 이는 **키워드·규칙 기반 검색어 해석**이지 자연어 모델을 학습한 기능은 아닙니다.

## 6. 프로젝트 구조

```text
omechu/workspace/
├─ index.html           # 홈 / 추천 진입
├─ page/                # 결과·위키·지도·계정 관련 화면
├─ css/                 # 화면별 스타일
├─ js/
│  ├─ index.js          # 추천 조건과 홈 인터랙션
│  ├─ result.js         # 추천 결과·상태 처리
│  ├─ wiki.js           # 위키 탐색·필터·정렬
│  └─ map.js            # 지도·검색
├─ backend/
│  ├─ api/              # PHP 엔드포인트
│  └─ config/           # DB 연결 설정
└─ assets/              # UI 이미지·리소스
```

> 이 디렉터리는 `Web` 저장소의 하위 프로젝트입니다. **정적 HTML 파일만 열어서는 PHP API와 DB 기능이 실행되지 않습니다.** PHP 실행 환경, 해당 DB 스키마·데이터, 외부 API 설정 등이 별도로 필요합니다.

## 7. 결과와 검증 수준

**확인 가능한 산출물:** 추천 홈·결과·위키·지도·로그인 등 복수 화면, 조건별 메뉴 조회 PHP API, 브라우저 상태 전달, 외부 지도·음식 데이터 연동 코드, MVP 기획·SQL 스크립트.

**추가 확인이 필요한 항목:** 전체 시연 영상, 실제 PHP/DB 실행 환경의 엔드투엔드 테스트, 브라우저·모바일 호환성, 추천 결과의 정확성 및 사용자 평가, 기능별 개인 기여와 협업 범위.

현재 공개 소스만으로는 **사용자 증가, 추천 만족도 개선, 운영 성과**를 주장하지 않습니다.

## 8. 돌아보며 — 다음 개선 항목

1. **추천 조건 일치:** UI의 다중 선택과 API의 단일 파라미터 처리 차이 해소
2. **검색 데이터 구조:** JSON 문자열 `LIKE` 검색에서 관계형 테이블 또는 적절한 JSON 질의로 개선
3. **사용성 검증:** 빈 결과·네트워크 실패·로그인 상태 만료·지도 권한 거부 등 주요 경로 테스트
4. **외부 API 안전성:** 키를 환경변수로 분리하고 SSL 인증서 검증, 응답 검증, 요청 제한을 점검
5. **실행 증거:** 페이지별 스크린샷, 짧은 시연 영상, 기능별 테스트 기록 추가

## 9. 포트폴리오에서의 의미

오메추는 AI 모델 개발 프로젝트가 아니라 **일반 웹서비스의 사용자 요구를 화면·API·데이터베이스·외부 서비스의 흐름으로 구체화한 MVP**입니다.

AI 애플리케이션을 구축할 때도 필요한 기본기인 **데이터 요청과 상태 관리, 백엔드 응답 계약, 사용자 탐색 흐름**을 학습·적용한 보조 사례로 소개합니다.

> **기여도 안내:** 공개 코드만으로 공동 작업 여부와 개인별 작성 범위를 확정할 수 없어 모든 기능을 단독 개발했다고 단정하지 않았습니다. 작업 기록이나 커밋별 기여 근거가 확보되면 역할을 더 구체화할 수 있습니다.
